## État à la fin de session

Le deck utilise `assets/cassette-mechanism-pixel-v95.png` comme artwork principal. Les contrôles PREV / PLAY / STOP / NEXT / AUTO sont des hotspots HTML positionnés sur les boutons dessinés dans le PNG. Les backlights PNG sont présents dans `assets/`.

Les reels animés utilisent `assets/cassette-reel-pixel-v81.png`. Cet asset est bien le bon asset complet avec les grandes dents. La réduction précédente à ~72 px était une erreur : elle donnait l'impression qu'un petit rotor tournait au centre alors que les grandes dents restaient visuellement fixes.

Le correctif actuel est dans `css/deck-motion-fix.css` :

- reel à `width: 10.8%` (~166 px sur le V95 1536 px),
- centres conservés à environ `(426,430)` et `(844,430)`,
- rotation linéaire,
- gauche 2.91 s / droite 1.46 s,
- opacité PLAY ~0.90,
- `mix-blend-mode: normal`.

Commit principal du correctif dents : `f3a20178a07c8cb1a2129c036ee85924377a4b85`.

## PRIORITÉ ABSOLUE À LA REPRISE : cache + assainissement du code

Ne pas reprendre le polish visuel avant d'avoir stabilisé le chargement et réduit les couches transitoires. Le code actuel fonctionne par accumulation de rustines et devient difficile à diagnostiquer correctement.

Signes de dette technique déjà identifiés :

- `index.html` charge des CSS/JS statiques non versionnés ;
- `bootstrap.js` recharge dynamiquement certains de ces mêmes CSS/JS avec une query différente ;
- le service worker a été transformé en kill switch temporaire ;
- `deck-refactor.js` reconstruit plusieurs éléments UI au runtime ;
- le même V95 est injecté dans `.cassetteDeckImage` et `.cassetteDoorPanel` ;
- plusieurs générations de géométrie V84/V95 coexistent ;
- `deck-refactor.css`, `deck-motion-fix.css`, `looper-polish.css` et `base.css` se surchargent mutuellement avec beaucoup de `!important` ;
- les vrais boutons transport existent encore en version legacy cachée pendant que des hotspots proxy les déclenchent ;
- le compteur est créé au runtime ;
- `deck-refactor.js` utilise encore un polling UI périodique ;
- les assets visuels critiques utilisent encore des URLs stables pouvant rester en cache HTTP navigateur/CDN.

Objectif de la prochaine session : revenir à une chaîne de chargement unique et à une architecture du deck lisible avant toute nouvelle feature graphique.

### Cible minimale après nettoyage

```text
index.html
  -> une seule déclaration de chaque CSS/JS
  -> URLs versionnées avec un BUILD_ID explicite pendant le dev

looper.js
  -> état audio / transport / boucle

deck-ui.js
  -> rendu du deck, classes d'état, compteur, backlights

deck.css
  -> géométrie V95 + responsive + animation reels

sw.js
  -> désactivé pendant le refactor
  -> réintroduit seulement après stabilisation
```

Le but n'est pas une grosse réécriture d'un coup : faire des commits courts, testables, et conserver le comportement fonctionnel à chaque étape.

Objectif : voir les grandes dents tourner, mais ne pas percevoir un disque différent collé sur la cassette.

## 2. Problème cache : toujours réel — cause identifiée

Le problème n'est pas seulement le service worker.

Le service worker a été désactivé pendant le développement (`sw.js` sert actuellement de kill switch et `bootstrap.js` désenregistre les workers + purge les caches `scratch-practice-*`). Cela ne suffit pas à éliminer le cache HTTP/browser.

### Cause principale actuelle

`index.html` charge encore directement, SANS query de version :

```html
<link rel="stylesheet" href="./css/base.css">
<link rel="stylesheet" href="./css/looper-polish.css">
<link rel="stylesheet" href="./css/deck-refactor.css">
<link rel="stylesheet" href="./css/clean-ui.css">
...
<script src="./js/bootstrap.js"></script>
<script src="./js/core.js" defer></script>
<script src="./js/looper.js" defer></script>
<script src="./js/looper-polish.js" defer></script>
<script src="./js/deck-refactor.js" defer></script>
...
```

Donc `bootstrap.js` lui-même peut être servi depuis un cache HTTP ancien. Si c'est le cas, sa logique `Date.now()` ne s'exécute même pas dans sa version récente.

En plus, `bootstrap.js` ajoute dynamiquement une deuxième copie versionnée de plusieurs fichiers (`looper-polish.css`, `deck-refactor.css`, `deck-motion-fix.css`, `looper-polish.js`, `deck-refactor.js`). Cela crée un mélange de ressources non versionnées + versionnées et complique fortement l'ordre CSS/JS et le diagnostic visuel.

### Les images cassette sont également non versionnées

Dans `index.html` :

```html
<img class="cassetteReel ..." src="assets/cassette-reel-pixel-v81.png">
```

Et `js/deck-refactor.js` impose :

```js
const DECK_ASSET_V95 = "assets/cassette-mechanism-pixel-v95.png";
```

Les backlights sont eux aussi chargés par des URLs stables sans query.

### Correction recommandée

Ne plus empiler des rustines de cache.

1. Choisir UNE seule stratégie de chargement.
2. Mettre un token de build directement dans `index.html` sur TOUS les CSS et JS qui y sont déclarés, y compris `bootstrap.js`.
3. Supprimer les inclusions dynamiques en double de `bootstrap.js` ; ne garder qu'une source de vérité.
4. Versionner aussi les URLs d'assets visuels sensibles (`V95`, `V81`, backlights`) pendant le développement, ou leur donner un nouveau nom quand leur contenu change.
5. Laisser le service worker désactivé jusqu'à stabilisation du deck.
6. Une fois stable, réintroduire un SW simple, testé séparément.

Important : le cache-busting `Date.now()` dans `bootstrap.js` ne peut pas résoudre un `bootstrap.js` lui-même mis en cache.

## 4. Armature / porte cassette

Le V95 contient déjà une grande partie de l'armature visuelle. Le DOM conserve encore le système hérité V84 :

- `.cassetteDoorPanel`
- `.cassetteDoorCavity`
- `.cassetteDoorGlass`
- `.cassetteDoorLip`
- `.cassetteDoorAssembly`

`deck-refactor.js` remplace actuellement à la fois `.cassetteDeckImage` ET `.cassetteDoorPanel` par le V95 complet. On a donc potentiellement une copie V95 complète clippée par-dessus une autre.

La `.cassetteDoorLip` CSS censée masquer le bas de la cassette est aussi trop petite / mal adaptée au V95 (`left:23%`, `top:53.2%`, `width:35.8%`, `height:7%`).

Ne pas supprimer toute la porte d'un coup : les reels sont enfants de `.cassetteDoorAssembly`. La prochaine expérimentation conservatrice doit isoler la duplication du panel avant d'enlever les autres couches.

## 5. Nettoyage architecture

À faire immédiatement après la correction de la chaîne de chargement, avant de reprendre le polish visuel :

- centraliser toute la géométrie V95 dans une seule feuille ;
- intégrer `deck-motion-fix.css` dans la feuille du deck puis supprimer le fichier temporaire ;
- supprimer les duplications CSS/JS chargées à la fois statiquement et dynamiquement ;
- déplacer les vrais boutons sémantiques dans la couche artwork et supprimer les proxies / legacy transport ;
- déplacer le compteur dans le HTML ou dans un module UI unique, mais ne plus le reconstruire dans plusieurs couches ;
- remplacer le polling UI 120 ms par des refresh explicites déclenchés par les changements d'état ;
- isoler état/audio (`looper.js`) et rendu (`deck-ui.js`) ;
- supprimer progressivement les overrides/no-op hérités et réduire fortement les `!important` ;
- supprimer les restes V84 uniquement après vérification que V95 couvre bien le besoin visuel.

Faire un commit testé à la fois, desktop + smartphone.

## 6. Idée UI pour la suite : enceinte de monitoring couchée dans le bas du deck

Concept proposé : remplacer la partie basse actuellement peu utile / visuellement faible par une enceinte de monitoring pixel-art couchée horizontalement, intégrée au châssis comme un vrai élément hardware.

Direction recommandée :

- une enceinte unique, large et basse, cohérente avec le langage pixel-art du V95 ;
- woofer principal visible + éventuellement petit tweeter / évent ;
- rétroéclairage amber très discret dans les interstices ou autour du woofer ;
- animation pilotée par le niveau audio réel du Looper (AnalyserNode / VU existant), pas par une animation CSS autonome ;
- le woofer doit pulser très peu : environ 1–3 % de variation de scale maximum, avec attack rapide et release plus lente ;
- le rétroéclairage peut réagir un peu plus que la géométrie pour donner l'impression de puissance sans transformer l'enceinte en élément cartoon ;
- idéalement séparer l'asset statique de la membrane mobile afin d'animer seulement le cône et conserver le cadre parfaitement stable ;
- éviter un pulse strict sur chaque kick : utiliser l'enveloppe réelle du signal, éventuellement pondérée vers les basses, pour que le mouvement suive naturellement le beat ;
- garder la possibilité de désactiver/réduire le mouvement avec `prefers-reduced-motion`.

Avant implémentation, produire un mockup directement sur une capture du deck réel afin de vérifier encombrement, proportions et cohérence avec la cassette. Ne pas générer un composant isolé puis essayer de le faire rentrer après coup.

Cette idée vient après les corrections prioritaires cache + nettoyage code + reel + armature ; ne pas l'utiliser pour masquer les problèmes actuels du deck.
